Bloques 1, 2 y 3 · Información Empresarial, ERP y CRM

1. Tratamiento de la información y silos de datos

En organizaciones no integradas se produce el fenómeno de las múltiples verdades debido al uso de hojas de cálculo aisladas (ej. clientes.xlsx vs. copias locales desactualizadas). Esto genera silos de datos, inconsistencia y pérdida de tiempo.

  • Dato: Pieza elemental sin procesar (ej. un teléfono).
  • Información: Dato contextualizado con significado (ej. teléfono de cobro de un cliente moroso).
  • Integración: Conexión de flujos de datos en tiempo real entre departamentos.

2. Sistemas ERP (Enterprise Resource Planning)

Pregunta directriz: ¿Cómo ejecuto y coordino la operación interna?

Coordina y modela los procesos de negocio en una base de datos centralizada y relacional. Es modular (se activan áreas según necesidad) y garantiza trazabilidad transversal: un pedido de venta genera automáticamente una reserva en inventario y un borrador en facturación.

3. Sistemas CRM (Customer Relationship Management)

Pregunta directriz: ¿Cómo capto, gestiono y fidelizo la oportunidad comercial?

Gestiona el ciclo de vida del cliente. Sus componentes clave son:

  • Lead / Iniciativa: Contacto inicial sin cualificar comercialmente.
  • Oportunidad: Posible venta cualificada con importe estimado y probabilidad de cierre.
  • Pipeline (Embudo): Fases visuales por las que avanza una oportunidad.
  • Actividades: Tareas programadas (llamadas, emails, reuniones) para evitar abandono comercial.
Integración ERP + CRM (El caso ByteSchool): ByteSchool solicita 20 teclados → CRM abre oportunidad → se cualifica y gana → ERP (Ventas) confirma pedido → Inventario despacha → Facturación emite cobro. Forman una única historia continua.

5. Tipos de licencias de software

Trampa habitual: GRATIS ≠ LIBRE, y OPEN SOURCE ≠ COSTE CERO. El coste de propiedad engloba implantación, hardware, consultoría y mantenimiento.
  • Software Propietario: El titular restringe derechos de acceso, modificación y redistribución.
  • Software Libre: Garantiza las 4 libertades básicas del usuario según la Free Software Foundation.
  • Open Source: El código fuente está disponible públicamente bajo licencias avaladas por la OSI.
  • Diferenciación Odoo 19:
    • Community: Licencia GNU LGPLv3, código abierto, sin coste de licencia.
    • Enterprise: Licencia Odoo Enterprise Edition License v1.0, código fuente compartido bajo suscripción comercial obligatoria.

6. Modelos de Despliegue

  • Monopuesto / Standalone: Todo en un PC local; solo para pruebas elementales.
  • Cliente-Servidor On-Premise: Servidor bajo control directo de la organización. Aporta máximo control pero exige plena responsabilidad en seguridad, parches y backups.
  • Cloud (IaaS): Alquiler de infraestructura (servidores virtuales). Se administra el SO y la aplicación.
  • SaaS (Software as a Service): El proveedor aloja y mantiene la plataforma, la base de datos y la seguridad; el cliente solo consume la solución vía navegador.
Decisión para RetroByte: Se implanta Odoo 19 Community en Máquina Virtual On-Premise de laboratorio (Ubuntu Server 24.04 LTS + PostgreSQL) para permitir el estudio integral de la arquitectura y el desarrollo futuro de módulos en 2.º DAM.

Bloques 7, 8 y 9 · Arquitectura Odoo 19, SO, SGBD y Auditoría VM

7. Arquitectura de 3 Capas de Odoo

  1. Capa de Presentación (Cliente Web): Navegador que procesa HTML5, CSS y JavaScript. Muestra la interfaz y recoge eventos.
  2. Capa de Aplicación (Servidor Odoo): Motor Python con ORM (Object-Relational Mapping), modelos, lógica de negocio y control de accesos.
  3. Capa de Datos (PostgreSQL): SGBD relacional donde reside toda la persistencia.
Regla de seguridad: El navegador NUNCA se conecta directamente a PostgreSQL. Las peticiones pasan siempre por el servidor Odoo para validar permisos y reglas de negocio.

8. Sistema Operativo y SGBD

  • Sistema Operativo: Ubuntu Server 24.04 LTS (Noble Numbat). Es el estándar compatible oficialmente con el paquete .deb de Odoo 19.
  • SGBD: PostgreSQL. La documentación oficial de Odoo 19 exige PostgreSQL 13 o superior para instalaciones desde código.

Bloques 11 y 12 · Documentación Técnica, Incidencias y Proyecto RetroByte

10. Registro Profesional de Operaciones

Un técnico debe saber explicar y demostrar lo que ha hecho. Un registro formal consta de 6 campos:

  • Objetivo: ¿Qué pretendo comprobar o ejecutar?
  • Acción: ¿Qué comando o procedimiento exacto aplico?
  • Resultado: ¿Qué salida devuelve textualmente el sistema?
  • Interpretación: ¿Qué significado técnico tiene esa salida?
  • Evidencia: Identificador unívoco de la captura de pantalla asociada (ej. CAP-03).
  • Estado: Correcto / Incorrecto / Pendiente.

11. Tratamiento Metodológico de Incidencias

«No funciona» o «No puedo entrar» es un SÍNTOMA (percepción del fallo), NO un diagnóstico.

El ciclo estructurado de resolución incluye:

  1. Síntoma: Manifestación observable del fallo.
  2. Impacto: Efecto operativo en el negocio o laboratorio.
  3. Diagnóstico: Causa técnica raíz demostrada (ej. servicio PostgreSQL en estado inactive).
  4. Solución: Intervención aplicada (ej. sudo systemctl start postgresql).
  5. Verificación: Comprobación posterior que demuestra que el servicio responde (ej. systemctl is-active devuelve active). Una incidencia nunca se cierra sin verificación previa.

12. Calidad de las Evidencias (Test de los 5 Segundos)
